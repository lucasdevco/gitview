# 产品需求文档

状态：实现中
阶段：Web MVP
目标产品：由 `gitview serve` 启动的本地优先 Web 应用

## 1. 产品愿景

gitview 从 Git 历史和代码结构中回答三个问题：

1. 谁在贡献，贡献发生在什么时间和代码区域？
2. 哪些文件与函数变化频繁、风险高、正在腐化或缺少维护者？
3. 一个新成员、维护者或技术负责人应该先关注哪里？

它不是员工绩效排名工具。单纯的代码行数无法代表贡献质量，默认输出应提供上下文并避免制造错误激励。

## 2. 目标用户与高频场景

### 2.1 技术负责人 / Tech Lead

- 查看日、月和自定义日期范围内的活跃趋势。
- 识别知识集中、单点维护和人员离开风险。
- 找到高频修改且复杂度高的代码热点，安排重构。
- 在迭代复盘时解释代码变化量突然上升的原因。

### 2.2 项目维护者

- 快速找到某个目录、文件或函数最熟悉的人。
- 了解最近一次修改、主要作者和变更轨迹。
- 判断长期无人维护但仍频繁被依赖的代码。
- 为 issue、重构或 code review 寻找合适参与者。

### 2.3 新加入项目的开发者

- 用一条命令了解项目结构、活跃模块和核心维护者。
- 查看函数级历史，理解“为什么这样写”和谁可能知道背景。
- 找到最值得先读的模块，而不是从文件树盲目开始。

### 2.4 个人开发者

- 回顾自己一段时间的工作轨迹。
- 查看主要投入在哪些模块、语言和函数。
- 发现重复返工、代码 churn 和未完成的重构区域。

## 3. 核心用户任务

### 完整产品方向：贡献趋势与人员维度

- 支持按日、按月聚合。
- 支持指定单日以及开始/结束日期筛选，边界日期包含在内。
- 支持按 author、committer 和归一化后的 person 查看。
- 展示提交数、活跃人数、新增、删除、净变化和 churn。
- 支持按路径、文件类型、语言、分支/引用筛选。
- 结果通过 Web UI 展示；排序与字段含义稳定。
- 能合并同一人的多个邮箱和用户名，支持 `.mailmap` 与用户配置别名。

### 完整产品方向：代码与函数分析

- 列出仓库中的语言、目录、文件和函数/方法。
- 对函数展示：位置、语言、签名、当前行数、复杂度（语言支持时）、最近修改时间、修改次数、主要贡献者。
- 支持查看某函数在日期范围内的新增、删除、churn 和贡献者变化。
- 支持按函数名、路径、语言、贡献者、活跃时间筛选。
- 函数移动或重命名后尽量延续历史；无法确定时标记置信度，不伪装为精确结果。
- 不支持函数解析的语言降级到文件级分析，并明确提示。

### 完整产品方向：热点与维护风险

- 代码热点：变更频率 × 代码规模；后续可叠加复杂度。
- 所有权集中度：主要贡献者占比、贡献者数量、bus factor 近似值。
- 陈旧代码：长时间未修改，且仍处于核心路径或历史上高变更。
- 高频返工：短周期内同一文件/函数反复修改。
- 大提交和异常变更：帮助用户定位统计峰值背后的 commit。
- 每个风险结论都能下钻到 commit、文件或函数证据。

### 后续产品方向：所有权与协作

- 生成目录/文件/函数的知识地图和推荐 reviewer 候选人。
- 区分“历史主要作者”“近期维护者”“最后修改者”。
- 识别无人维护区域、跨团队共享区域和所有权交接趋势。
- 支持排除机器人、vendor、生成代码、锁文件和指定路径。
- 提供仓库健康摘要，而不是只有人员排行榜。

### 后续产品方向：对比与解释

- 对比两个日期区间，例如本月与上月、版本 A 与版本 B。
- 查看新增/删除最多、churn 最大、复杂度增长最快的模块与函数。
- 解释指标变化：列出主要 commit、主要路径和主要贡献者。
- 支持按 tag、commit、branch 或 revision range 分析。

### 后续产品方向：使用体验

- 首次运行无需配置；自动识别仓库根目录与主要语言。
- 大仓库运行时显示阶段和进度，可取消。
- 缓存历史与解析结果，增量分析新 commit。
- 配置文件可提交到仓库，保证团队统计口径一致。
- 结果中显示本次分析采用的 revision、过滤条件、时区和口径版本。

### 远期产品方向：生态与可视化

- 生成静态 HTML 报告和趋势图。
- 可选接入 GitHub/GitLab 的 PR、review、issue 数据；与纯 Git 指标分层展示。
- 多仓库或 monorepo 子项目对比。
- CI 基线检测，例如热点或复杂度显著恶化时给出提示。
- 插件化语言分析器和自定义指标。

## 4. 最痛的需求排序

综合频率、价值和仅靠普通 Git 命令难以完成的程度，建议优先：

1. **身份归一化**：同一个人多个邮箱会让所有人数和 ownership 失真。
2. **函数级历史**：用户想知道“谁懂这个函数”，而不只是“谁改过这个文件”。
3. **热点 × 复杂度**：单看代码量信息密度低，变化频繁又复杂的代码才最值得处理。
4. **可解释下钻**：每个趋势峰值或风险结论必须能追溯到具体 commit。
5. **大型仓库性能**：全量扫描慢会直接导致工具被放弃，缓存是核心能力而非后期优化。
6. **排除噪声**：生成代码、依赖、格式化提交和机器人会污染结果。
7. **时间与 revision 可复现**：同一条命令应明确“分析了哪个版本、哪个时区、哪些引用”。

## 5. 首个命令行入口

前期只实现一个命令：

```text
gitview serve [repository]
```

- `repository` 省略时使用当前目录，并自动定位 Git 仓库根目录。
- 服务默认监听 `127.0.0.1:8080`，启动后输出可访问的 HTTP 地址。
- 支持 `--port` 覆盖端口；固定只监听 loopback，不提供 `--host`，前期不自动打开浏览器。
- Contributors、Functions、Hotspots、Ownership、Compare、Explain 等均是 Web 页面或后续页面能力，不创建同名 CLI 子命令。

### 5.1 已实现的 Web MVP

首个可运行版本从 Overview 垂直路径扩展为以下本地 Web 页面：

```text
启动本地服务 → Overview/筛选 → Contributor → 文件 Hotspots/Ownership → 多语言 Functions → Compare/Explain
```

包含：

- 仓库名称、根目录、当前分支和 HEAD。
- commit 数、贡献者数、additions、deletions、churn。
- 简单的按月提交趋势、贡献者列表和最近提交列表。
- 分析中、空仓库、非 Git 仓库和 Git 调用失败状态。

当前限制：

- 函数解析只支持 Go，历史 lineage 为 `probable`，不保证跨移动/重命名精确。
- SQLite 增量索引、SSE、后台 watcher、OpenAPI 代码生成。
- JSON/CSV 导出、配置文件、多仓库和远程平台集成。

## 6. 非目标（首个版本）

- 不根据 Git 指标评价员工绩效或产出质量。
- 不保证跨任意语言精确追踪函数重命名、拆分和合并。
- 不在纯本地模式推断 PR、review、issue 等 Git 中不存在的信息。
- 不做完整静态分析、安全扫描或依赖漏洞扫描。
- 不承诺首版支持所有编程语言。

## 7. 首个 Web MVP 验收标准

- `gitview serve` 在有效 Git 仓库中启动后输出明确的本地访问地址。
- 浏览器可以打开 Overview，并看到与 Git 抽样结果一致的基础统计和最近提交。
- 服务只监听 loopback；不执行仓库代码、hooks 或构建脚本。
- 空仓库给出零结果；非 Git 目录和 Git 不可用给出可理解的错误。
- Ctrl-C 能关闭 HTTP server 和正在进行的分析。
- Go 测试覆盖仓库发现、Git 输出解析、统计聚合和 HTTP 最小契约；前端至少有一次生产构建验证。

## 8. 产品形态原则

- CLI 只负责启动本地服务和处理生命周期，不承载分析查询或展示逻辑。
- 贡献趋势、函数热点和 ownership 图谱统一通过本地 Web UI 呈现。
- HTTP handler 与 Web 组件不直接实现统计口径；指标计算保留独立 service 边界。
- 默认本地运行并监听 loopback；浏览源码和贡献数据不要求云端账户。
- 桌面应用是同一本地服务的可选外壳，不另建业务后端。
- 产品 UI 采用 agentsview 的高密度、数据优先、持续可见筛选和可下钻交互模式，详细流程见 [ui-interaction.md](./ui-interaction.md)。
